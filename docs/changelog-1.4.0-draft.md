# CHANGELOG draft for 1.4.0

The dev blocks of 1.3.8-dev.1 to 1.4.0-dev.4 stay in CHANGELOG.md for the whole
dev phase, because that is what testers on the dev images read to see what
changed between two builds. This file is the consolidated release block,
written into CHANGELOG.md in place of those dev blocks when the release build
is cut, not before. 1.3.8 was never released, so its dev builds belong to 1.4.0.

It is written for a reader of 1.3.7. A fix of something that only ever existed
in a dev build is not a fix to that reader, so those are folded into the
feature they belong to or left out; the dev blocks keep them. Every dev build up
to 1.4.0-dev.4 is in; every dev build after that, and what sits under
Unreleased then, has to be folded in here as well.

## Draft

-----------------------------------------------------------------------------------------------
Version 1.4.0
   - Breaking:
      - The image runs as the unprivileged user `node`, uid and gid 1000, instead of root, and nothing in the container runs as root any more, `docker exec` and `debug-printers` included. A compromised service can no longer act as root inside the container (issue #267)
         - An installation on a Linux host or a NAS with bind mounted `printers/` and `logs/` directories has to hand them to that user once, because everything the earlier images wrote there belongs to root: `sudo chown -R 1000:1000 <printers directory> <logs directory>` on the host. Until then the container stops on start and its log names the directories and this command, instead of failing on the first save
         - Docker Desktop on macOS and Windows needs nothing, a folder shared from the host is writable for every user in the container. Only a folder inside the WSL file system follows Linux permissions, and the same command is run in the WSL shell there
         - A named volume needs nothing. Another user is set with `user:` in the Compose file or `--user` on `docker run`, and the directories then belong to that user
   - Deprecated:
      - The old image name ghcr.io/rdiger-36/bambulab-ams-spoolman-filamentstatus receives its last release before 1.5.0. From 1.5.0 on, every version is published as ghcr.io/rdiger-36/haspelsync only. A container that runs from the old name says so with this version in its log, in the dialog on the dashboard and under System on the settings page, where it said "for a transition period" before. `/api/notices` carries the version as `stopsAt` in `legacy-image`, `/api/system` as `imageStopsAt`
   - New Features:
      - An original Bambu Lab spool is linked through Spoolman's own tags. Spoolman 0.27.0 and newer hold the tag of a spool natively, and a spool created or merged against such a Spoolman gets the serial number of its RFID chip as a native tag. A native tag belongs to one spool only, so two records can no longer claim the same physical spool the way two equal extra fields could. The extra field `tag` is still read, a spool linked before is recognised exactly as it was, and an older Spoolman is linked through the extra field as before. Based on the proposal in PR #254
      - Spools linked before can be migrated. The "Spool tags" card in the Spoolman section of the settings says how many spools carry their tag only in the extra field, and "Migrate now" gives each of them the native tag, archived spools included. The extra field stays in place, so the migration can be repeated and nothing that reads the field stops working. A spool that shares its tag with another one is listed with the spool that holds it rather than migrated. The dashboard offers the same migration once, the first time it finds spools to migrate
      - "Also write extra.tag" in the advanced part of the Synchronisation card, on by default (`WRITE_EXTRA_TAG`). Switched off, a new or merged spool is linked through the native tag alone, for an installation where nothing else reads the extra field. It changes what is written, never what is read
      - A tag another tool put on a spool is left alone. An NFC sticker, an OpenPrintTag or the chip number of a Bambu Lab spool does not make the spool count as linked: it can still be merged, and "Never merge a tagged spool" looks only at the link this service writes
      - "Clear extra fields" on the same card empties the extra field on the spools that carry the same tag natively. It is offered only once every spool is migrated and "Also write extra.tag" is off, it asks first, and a spool that could not be migrated keeps its field. Nothing needs it: the field can stay for good
      - `GET /api/spoolman/tags`, `POST /api/spoolman/tags/migrate` and `POST /api/spoolman/tags/cleanup` report and run both over the API
      - The header of the AMS 3H shows humidity and temperature of its two compartments the way Bambu Studio does: the seven ordinary slots together, the drying slots 6 and 8 (`E6`, `E8`) on their own. The unit itself reports no reading, only its zones, and the dryer is the zone of two slots, which is how Bambu Studio tells it apart (issue #262)
      - Running dryers get a card of their own above the slot tables, one row per unit, on the AMS 2 Pro, the AMS HT and the AMS 3H alike: what the dryer is doing, the temperature and filament it was set to, a progress bar where the setting says how long it runs, and the time left in hours and minutes. The state is read the way Bambu Studio reads it, so a dryer cooling down after its cycle or stopped by an error says so instead of disappearing. The card folds like a unit and keeps a count per kind while folded (8× drying, 1× cooling, 2× error), the header of a drying unit carries a mark, and the card is gone while nothing dries. `/api/status` carries the state as `status` and `phase` in `drying`
   - Fixes:
      - A spool archived by hand in Spoolman while it still sits in its slot is recognised by its native tag, also with "Archive empty spools" off. It reads "Loaded (archived)" instead of being offered as a new spool
      - A slot that is linked to a spool no longer names a spool it could be merged with. After an automatic merge the API reported the spool the slot had just been linked to as `mergeableSpool` as well, until something else changed the slot, and a slot with an assigned spool kept its merge candidate
      - A print of a file that was changed and sent again under the same name is weighed from the new file. The printer can keep both copies, one in its cache and one on the storage root, and the service read whichever name it tried first, which could be the old file. It now asks the printer when each copy was written and reads the newest (issue #252)
      - A spool that an AMS refill ran empty no longer keeps its slot's assignment. The assignment is what links a spool without an RFID tag to its slot, and it stayed after the spool ran out, so the next spool of the same filament put into that slot was booked on the empty one. It is released at the end of the print, and only after a refill: a spool taken out by hand, to be dried for example, keeps its slot as before (issue #225)
      - The report of such a print says when Spoolman still lists weight on the spool that ran out, which happens when its starting weight was too high, and offers to set it to 0 g or to archive it. The print card links to it until that is done. The weight is not changed on its own, since that would book filament that was never printed (issue #225)
      - The H3C is supported. Its AMS 3H reports as one unit with nine slots under a unit number no other AMS uses, and every one of its slots was named "Z": the slots could not be told apart, merging a spool failed with "Cannot read properties of null", an assignment landed on whichever "Z" slot came first and a print was booked on no spool at all, because the slot it ran from was reported in the same numbering. The nine slots are now `E1` to `E9`, the slot a print runs from is read in that numbering, and the AMS 3H is named as such once the printer has said which units it has. The dashboard shows it as one table of nine slots under "AMS 3H E" instead of three tables of four, four and one. The units stand in a fixed order, `A` to `E`, then the AMS HT units, then the holders, whatever order the printer reports them in. `A1` to `D4` stay free for the AMS units that can be connected to its first tool (issue #262)
      - An empty slot of the AMS 3H is shown as empty. It reports one field more than the empty slot of any other AMS, and that field made it look like a 3rd party spool waiting for an assignment (issue #262)
      - The H3C reports a spool holder for each of its nine tools. The first two keep the labels `External` and `External-2` every dual nozzle printer has, the others are `External-3` to `External-9`. Not seen with a spool on it yet (issue #262)
      - The slot a print runs from, as `/api/status` reports it, is no longer read from `tray_now` on a printer that names it per nozzle. The H3C sends both, and its `tray_now` counts the slots within its unit, which read as a slot of the first AMS (issue #262)
      - Merge, Create and Create with filament on a slot that has nothing to write from answer with a message saying so, in the language of the Web UI, instead of "Cannot read properties of null". That happens on a page that is no longer current, and it happened on every merge on an H3C, where all slots shared one label (issue #262). Two slots under one label are refused rather than written to whichever comes first. Over the API these answers are a 409 with a `code`
      - The anonymised diagnostics export masks three more values in the raw MQTT trace: the chip number of an RFID spool (`tag_uid`), the serial numbers of the hotends and the printer's LAN address, which the printer reports as a number rather than in dotted form. The chip number keeps its first four characters like the tag of a spool, the all zero placeholder of a slot without a chip stays, and the address keeps its subnet like every other address in the export (issue #262)
      - A filament printed from a slot without an assigned or tag linked spool is no longer booked on another spool of the same filament. When the printer or Bambu Studio names the slot a filament runs from, that slot is the only one considered: without a spool to book on, the filament is skipped and the print summary asks for an assignment. Before, the service looked for another slot with the same profile and colour and booked the grams there, so with two identical spools loaded and only one assigned, the assigned one was charged for what the other printed (issue #273)
      - The log line and the print summary name the slot the booked spool sits in. Where the service had to find the spool by colour, they named the slot the filament was estimated to come from, which made it look as if the spool sat there (issue #273)
      - After a print, the dashboard says "not booked" under the grams of a slot nothing was booked from. It said "booked" on every slot the print used as soon as anything of the print was booked, so a slot without a spool read "not tracked" and "booked" at the same time (issue #273)
      - An AMS refill on an A1 or a P1 is booked on both spools. These printers never report which slot a running print takes its filament from, only the slots Bambu Studio sent the job to, so when the AMS switched to another slot of the same filament, the whole print was booked on the spool that ran out. The switch is now read from the slot the printer prints from: when it moves to a slot the job was not sent to while the print runs, the spool that ran out gets the layers before it and the spool in the new slot the rest, the same way a refill on the other printers is split. A switch before the first layer, a spool found empty while the job loads, books the whole print on the new slot. A refill onto a slot the same job prints other parts from cannot be told apart from a colour change and is still booked whole on the spool that ran out (issue #273)
      - A spool that is not one of Bambu Lab's Translucent lines is no longer created as a translucent filament. A white PETG Basic spool became PETG "Clear": the filament catalogue has no Basic line for PETG, which leaves "White" and "Clear" with the same colour, and "Clear" won because it comes first. The catalogue marks its translucent entries, and a slot now keeps to its side as long as the catalogue has an entry of the same colour there. A Translucent spool still gets its translucent entry (issue #278)
